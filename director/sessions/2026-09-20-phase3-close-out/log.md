# Session log — 2026-09-20-phase3-close-out

Plain-English narrative companion to `state.json` in this same session folder. See plan §3.5.

**Context.** Picking up mid-Phase-3 of the EirePolitic Director implementation. Phase 3's job (plan §3.2-§3.4): give every render project a shared result shape, shared declarative QA, a shared review-page builder, and one generic dispatchable render workflow — instead of every content product hand-writing its own bespoke 200-line workflow.

**Batched-checkpoint model adopted.** Warren asked that manual steps be queued and handed off in batches instead of raised one at a time. This session found the actual permission boundary by testing it directly: pushing a *new* GitHub Actions workflow file that uses real AWS production secrets is blocked by the platform's own permission classifier and needs Warren; everything else — code, config, docs, branches, ordinary PRs, and (confirmed later this session) *dispatching* an AWS-credentialed workflow that's already on `main` — does not.

**Pure-code build.** Built `contract.py` (the shared `RenderResult` shape), `normalize.py` (per-project shims for both adapters' very different raw return shapes), `qa.py` (a declarative QA runner reading each project's own `project.yml` `qa:` block), `review_page.py` (one HTML review-page builder replacing every hand-written heredoc), and `render_pipeline.py` (the orchestration entrypoint). Verified locally against hand-built synthetic fixtures shaped to match both adapters' real, documented return values — including negative-path tests proving each QA check actually detects a failure it's supposed to catch. One real bug caught this way: captions were staged to disk but never wired into the HTML template — fixed before merge. Merged via PR #145, squash commit `b7b7311b`. CI (`director_factory_v1_identity_ci.yml`) stayed green, confirming none of the frozen v1 files were touched.

**Batch 1 — handed to Warren, closed same day.** The one artifact needing AWS secrets — `.github/workflows/instagram_factory_render.yml` — was drafted, syntax-validated, and handed to Warren in full (file content + click-by-click steps) via `claude/phase3-batch1-instructions.md`. He added the file and ran it twice within the hour: `party_issue_monthly_profile_v2` (resolved to 2026-08, the last completed month) and `ipi_polling_factory_v1` (resolved to its latest poll date). Both completed with `conclusion: success` and full declarative-QA PASS.

**Closing the exact acceptance wording.** Neither of Warren's two dispatches was the July 2026 period specifically named in the plan's Phase 3 acceptance criterion (he correctly left `period` blank per the instructions, so it resolved to each project's own default). Rather than ask Warren for a third dispatch, this session tried dispatching the now-merged workflow directly — and it went through with no permission denial. That's a materially useful finding on its own: it means Phase 5's four v1 workflows, which reuse this same file, won't need Warren to dispatch routine renders going forward, only to push a *new* workflow file if one is ever needed. The direct July dispatch (`run 35526489717`) also came back QA PASS: 55/55 slides, 11/11 parties, matching the canonical reference's documented counts and the regression fixture's declared values.

**Outcome.** Phase 3 is complete. Plan doc (`claude/eirepolitic-director-implementation-plan.md`) updated to reflect this — status line, §8 phase table, §10 Batch 1 (now closed), and new §1.13 recording the verification results and the dispatch-vs-push permission finding.

**This session folder itself** is the first real exercise of Phase 4 (plan §3.5) — see `director/sessions/README.md` on `main` for the schema this file and `state.json` follow, and note the one deliberate deviation from the original plan sketch: session branches are created as `sly/session/<session-id>`, not `director/session/<session-id>` — the GitHub connector automatically prefixes every branch it creates with the account's configured `sly/` prefix, so the convention was adjusted to match what the tooling actually produces rather than fighting it.
