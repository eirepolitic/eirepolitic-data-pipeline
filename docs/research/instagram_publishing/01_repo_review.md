# Step 1 — Existing Repository Review

Status: **complete**

Scope: inspect the current Instagram generation pipeline and identify anything already relevant to future publishing. No production publishing changes were made.

## Existing Instagram workflow

The repository already contains a manual Instagram generation workflow:

- `.github/workflows/instagram_campaign_render.yml`
- `process/instagram_render_campaign.py`
- `process/instagram_build_copy_pack.py`
- `process/instagram_build_publish_queue.py`
- `process/instagram_upload_preview_to_s3.py`
- `process/instagram_generate_preview_links.py`

The current workflow is deliberately review-oriented and does not publish or schedule content.

## Existing review and publication gates

`process/instagram_build_publish_queue.py` already separates eligible and blocked items. It requires all of the following before an item enters its generated queue:

- `publish_ready` must be true/yes;
- `review_status` must be an approved/ready value;
- `safety_notes` must be empty.

The script explicitly documents that it creates a queue file only and that publishing must remain a separate explicit step after manual review.

This is a strong starting principle and should be preserved.

## Existing caption and alt-text handling

`process/instagram_build_copy_pack.py` already creates explicit deterministic files/fields for:

- caption text;
- alt text;
- hashtags;
- review state;
- safety notes.

This aligns with the desired future design: the final approved caption should be stored explicitly before publication and should not be regenerated by an LLM at publication time.

The current caption generation is campaign-specific and simple; later research will determine how reusable/versioned caption templates should fit around it.

## Existing S3 use

The GitHub workflow can optionally upload preview assets to the existing S3 bucket `eirepolitic-data`.

Current usage is clearly preview/review oriented. It should not automatically be treated as the canonical production publication store.

Later research must determine:

- a stable immutable approved-asset path;
- checksums/hashes;
- retention/versioning;
- how Meta retrieves media URLs;
- whether presigned S3 URLs are appropriate at execution time.

Temporary GitHub Actions artifact URLs should not become production publishing inputs.

## Existing GitHub Actions behaviour

`instagram_campaign_render.yml` is manual (`workflow_dispatch`) and currently performs:

1. render campaign;
2. build copy pack;
3. build gated queue;
4. optionally upload previews to S3;
5. upload workflow artifacts.

It explicitly states that it does not publish, schedule, or approve Instagram content.

This workflow should remain generation/review oriented unless later architecture work gives a strong reason to change that boundary.

## Existing AWS credential assumption

The workflow currently consumes static GitHub repository secrets:

- `AWS_ACCESS_KEY_ID`
- `AWS_SECRET_ACCESS_KEY`
- `AWS_REGION`

This is relevant to the future secrets/infrastructure review. We should not automatically extend this credential pattern to publishing. GitHub OIDC to AWS should be evaluated later as a safer alternative for deployment/CI access.

## Existing publishing implementation

No direct Instagram/Meta publishing implementation was found in the reviewed Instagram pipeline files.

The current `publish_queue` is a generated CSV/manifest artefact, not a scheduler or delivery mechanism.

No live Meta token handling, Graph API publishing call, scheduled Instagram delivery, publication ledger, or production social-publishing state machine is currently present in the reviewed path.

## What should be reused conceptually

The strongest existing building blocks are:

- deterministic generated caption/alt-text outputs;
- explicit human review state;
- `publish_ready` gating;
- blocked-item reasons;
- manual workflow execution;
- existing S3 integration;
- the explicit separation between generation and real publication.

## What should not be assumed yet

Do not yet decide:

- whether AWS or a third-party service should schedule publication;
- whether the existing queue CSV becomes part of the final architecture;
- whether S3 preview paths become production asset paths;
- which Instagram account type/API path should be used;
- whether Meta credentials belong in GitHub or AWS;
- whether the existing personal Instagram account needs to be converted.

Those are covered by later research steps.

## Step 1 conclusion

The repo does **not** need a second parallel post-generation system. A future publishing layer should consume approved outputs from the existing generation/review pipeline and preserve its explicit review boundary.

The immediate next research step is the account constraint: verify whether the existing personal Instagram account can be converted to Creator or Business while retaining its existing followers, posts, handle, and history, and document any trade-offs before evaluating the API architecture around it.
